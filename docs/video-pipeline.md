# 视频处理流程

本文记录 BadmFrame 当前媒体工作流。技术栈由 [ADR-0002](decisions/0002-technical-architecture.md) 决定：iOS 使用 AVFoundation，Web 后端使用 FFmpeg，Web 前端使用浏览器 `<video>` 和 `<canvas>`。后续主产品形态优先考虑移动端本地运行，Web 主要用于测通链路、评估算法和验证工作流。

## 当前流程

1. 导入或上传源视频。
2. 校验文件是否可读取。
3. 提取时长、分辨率、帧率、编码等元数据。
4. 加载可浏览预览。
5. 生成或展示缩略图，辅助快速定位回合。
6. 在时间线上打时间点标记。
7. 手动或围绕标记选择片段起止时间。
8. 运行模型分析，自动生成有效回合候选和置信度。
9. 用户审查候选回合，确认、删除或微调边界。
10. 提交导出任务，展示进度、完成、取消或失败状态。
11. 保存项目、标记、片段、候选回合、审查结果和导出状态。

## 两端实现

| 操作 | iOS | Web |
|------|-----|-----|
| 导入 | PhotosUI 选择并拷贝到 App 沙盒 | 浏览器选择文件并上传到后端 |
| 元数据 | AVAsset 异步读取 | FFmpeg/ffprobe 服务端读取 |
| 播放 | AVPlayer 硬件解码 | HTML5 `<video>` |
| 缩略图 | AVAssetImageGenerator | 前端 `<canvas>` 或后端 FFmpeg |
| 裁剪导出 | AVAssetExportSession | Celery 任务调用 FFmpeg |
| 存储 | SwiftData + 沙盒文件 | MySQL + 本地 storage + Redis 进度 |

## 标记与片段

- MVP 标记是时间点，不改变原视频。
- 片段有起止时间、标题/标签、备注和可选锚点标记。
- 标记列表用于快速跳转，片段列表用于导出和归档。
- 复杂空间标注和高级球路可视化属于未来范围；模型回合候选是重启后的核心能力，但必须经过用户确认。

## 导出策略

- 默认保留音频。
- 默认优先速度，使用 stream copy；裁剪精度受关键帧间隔影响。
- 需要帧精度时再引入重新编码策略，并记录为决策。
- Web 导出异步执行，前端通过状态查询或 WebSocket 获取进度。

## 自动剪辑

旧智能剪辑基线见 [ADR-0003](decisions/0003-auto-dead-time-editing.md) 和 [自动剪掉死球时间](auto-dead-time-editing.md)。该路线已暂停，只保留为实验对照。

重启后的自动剪辑路线见 [ADR-0004](decisions/0004-rally-segmentation-by-shuttle-trajectory.md) 和 [基于球轨迹的回合切分](rally-segmentation.md)：以 TrackNetV3 球轨迹、自动主场地估计、轨迹连续性、球速/方向变化、状态机和人工审查为核心。核心目标是每个有效回合的候选边界误差小于 1s；第一版产品承诺是“候选回合需确认”，不是未经确认的一键生成最终视频。

Web 端当前用于跑通候选生成、审查、应用为 clips 和导出链路；算法质量和契约稳定后，应迁移到移动端本地推理和本地剪辑。

## 失败模式

实现视频能力时优先把失败显式暴露给用户：

- 不支持的媒体文件。
- 源视频缺失或权限失效。
- 元数据读取失败。
- 缩略图生成失败。
- 导出取消。
- 导出文件覆盖冲突。
- 编码进程失败。
- 磁盘空间不足。

## 未决问题

- 是否需要提供“高速裁剪”和“帧精度裁剪”两种导出模式。
- 第一批导出预设是否只保留原始质量，还是加入微信/小体积预设。
- 是否需要代理文件来改善超长视频预览。
- Web 端缩略图最终由前端生成、后端生成，还是混合策略。
- Windows 模型环境用 Docker、Conda 还是远端 GPU 作为第一落点。
- 移动端本地模型推理和本地剪辑如何在耗时、耗电、包体和硬件兼容之间取舍。

## Agent 注意事项

- 不要把大样例视频放进 git；测试视频应可解释、尽量小，并优先可再生成。
- 视频处理改动要覆盖成功、取消和失败状态。
- 涉及导出精度、转码策略、存储布局或后台任务模型变化时，需要新增或更新 ADR。
